# Control Flow Flattening (CFF)

## Overview

Control Flow Flattening is an obfuscation technique that destroys the natural hierarchical structure of a program's control flow graph. Instead of blocks flowing directly into each other (if/else, loops), all basic blocks are placed at the same level and dispatched through a central state machine.

## How It Works

### Original Control Flow

```
     [Block A]
      /     \
 [Block B] [Block C]
      \     /
     [Block D]
```

### After Flattening

```
         [Dispatcher]
       /   |    |    \
  [A]   [B]   [C]   [D]
   |      |    |      |
   +------+----+------+
              |
         [Dispatcher]
```

All blocks are siblings under the dispatcher, which uses a state variable (`rax`) to determine which block executes next.

## Technical Pipeline

### Step 1: Function Discovery

The PDB parser extracts all functions from the debug symbols:

```cpp
pdbparser pdb(&pe);
auto functions = pdb.parse_functions();
```

Each function record contains:
- `name` - Symbol name
- `offset` - Offset within the `.text` section
- `size` - Function size in bytes

### Step 2: Instruction Disassembly

Each function is disassembled using Zydis into `instruction_t` structures:

```cpp
struct instruction_t {
    int inst_id;                       // Unique instruction ID
    int func_id;                       // Parent function ID
    bool is_first_instruction;         // First instruction flag
    std::vector<uint8_t> raw_bytes;    // Raw machine code
    uint64_t runtime_address;          // Original virtual address
    uint64_t relocated_address;        // New address after relocation
    ZydisDisassembledInstruction zyinstr; // Zydis decoded instruction
    bool has_relative;                 // Has relative displacement
    bool isjmpcall;                    // Is a jump or call instruction
    struct {
        int target_inst_id;            // Target instruction ID
        int target_func_id;            // Target function ID
        uint32_t offset;               // Displacement offset in bytes
        uint32_t size;                 // Displacement size
    } relative;
};
```

### Step 3: Function Analysis

`analyze_functions()` resolves all relative references between instructions:
- Identifies which instruction each relative jump/call targets
- Detects jump tables (indirect jumps through register + offset patterns)
- Maps instruction IDs to their containing functions

### Step 4: Jump Table Detection

Functions containing jump tables (typically generated by `switch` statements) are marked and excluded from CFF:

```cpp
void remove_jumptables();
// Sets function_t::has_jumptables = true for affected functions
```

Jump tables use indirect addressing that would break under block shuffling.

### Step 5: Basic Block Construction

The CFF algorithm (`cfflattening.cpp`) identifies basic blocks:

```cpp
struct BasicBlock {
    int block_id;
    std::vector<instruction_t> instructions;
    int next_block;      // Fall-through successor
    int dst_block;       // Conditional jump target (-1 if none)
};
```

**Block boundaries are determined by:**
- Destinations of conditional jump instructions (block starts)
- Unconditional jumps, `ret` instructions, or the next conditional jump destination (block ends)

### Step 6: Block Shuffling

Blocks are randomly reordered to destroy the original sequential layout:

```cpp
// Pseudocode
std::shuffle(blocks.begin(), blocks.end(), rng);
```

### Step 7: Dispatcher Construction

A dispatcher is generated using `rax` as the state variable:

```nasm
; Enter dispatcher
push rax        ; Save state variable
pushf           ; Save CPU flags

; Dispatcher body
mov eax, 0      ; Initial state = first block ID
cmp eax, 0
jne check_1
; ... Block 0 code ...
pushf
mov eax, 2      ; Set next state
jmp dispatcher

check_1:
cmp eax, 1
jne check_2
; ... Block 1 code ...
pushf
mov eax, 3      ; Set next state
jmp dispatcher

; ... more blocks ...
```

**Key design decisions:**
- `pushf`/`popf` preserve CPU flags across dispatcher transitions
- `rax` is used as the state variable (saved/restored on stack)
- Each block sets the state variable to its successor's ID before jumping back to the dispatcher
- Conditional branches set the state variable to the conditional target's ID

### Step 8: Relocation

All obfuscated code is relocated to a new PE section (`.0Cff`, 10 MB allocation):

```cpp
auto new_section = pe.create_section(".0Cff", 10000000,
    IMAGE_SCN_MEM_EXECUTE | IMAGE_SCN_MEM_READ | IMAGE_SCN_CNT_CODE);
```

The relocation process:
1. Calculate new addresses for all instructions in the new section
2. Expand short jumps (8-bit displacement) to near jumps (32-bit displacement) when distance exceeds range
3. Patch all relative offsets to reflect new positions
4. Write trampoline `jmp` instructions at original function locations
5. Fill original function bodies with random bytes

### Step 9: Entry Point Obfuscation

The PE entry point is further protected using XOR and rotation encoding, stored in a separate `.0Dev` section.

## Effect on Decompilation

### Before CFF (IDA pseudocode)

```c
void target_function(char flag) {
    printf("Block A\n");
    if (flag) {
        do_something();
    } else {
        do_other();
    }
    return cleanup();
}
```

### After CFF (IDA pseudocode)

```c
__int64 sub_1400292F5(char a1) {
    int v8;
    __asm { pushf }
    v8 = 0;
    while (1) {
        while (v8 == 2) {
            __asm { popf }
            v16 = sub_140011217();
            __asm { pushf }
            v8 = 3;
        }
        if (v8) break;
        __asm { popf }
        // Block A code...
        if (v17) {
            __asm { pushf }
            v8 = 1;
        } else {
            __asm { pushf }
            v8 = 2;
        }
    }
    // ...
}
```

The decompiler sees a `while(1)` loop with state variable checks instead of the original structured flow.

## Limitations

- **64-bit PE only** - 32-bit binaries are not supported for CFF
- **Requires PDB** - Function boundaries must be known via debug symbols
- **Jump tables excluded** - Functions with `switch` statements using indirect jumps are skipped
- **Section size** - The new `.0Cff` section is allocated at 10 MB; very large binaries with many functions may exceed this
- **Performance overhead** - Dispatcher transitions add runtime cost (typically negligible for non-performance-critical code)
